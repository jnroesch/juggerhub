# Phase 1 Data Model: Media Storage Abstraction + Object Storage

**Feature**: 035 · **Date**: 2026-07-31 · **Plan**: [plan.md](./plan.md) · **Research**: [research.md](./research.md)

## Shape of the change

Three entities lose their byte column and gain a descriptor pair. Nothing else about them moves —
same tables, same keys, same foreign keys, same cascade deletes, same query filters. That continuity
is deliberate and load-bearing (research §6).

| Entity | Table | Owner FK | Before | After |
|---|---|---|---|---|
| `ProfileAvatar` | `ProfileAvatars` | `ProfileId` → `PlayerProfiles` (1:1) | `ContentType`, `Bytes bytea` | `ContentType`, `ObjectKey`, `SizeBytes` |
| `BadgeIcon` | `BadgeIcons` | `BadgeDefinitionId` → `BadgeDefinitions` (1:1) | `ContentType`, `Bytes bytea` | `ContentType`, `ObjectKey`, `SizeBytes` |
| `AchievementIcon` | `AchievementIcons` | `AchievementDefinitionId` → `AchievementDefinitions` (1:1) | `ContentType`, `Bytes bytea` | `ContentType`, `ObjectKey`, `SizeBytes` |

All three continue to derive from `BaseEntity` (UUIDv7 `Id`, audit dates via the interceptor).

## New fields

| Field | Type | Constraints | Purpose |
|---|---|---|---|
| `ObjectKey` | `string` | required, `HasMaxLength(200)`, **unique index** | Where the bytes live in the media store. Never leaves the backend (FR-013). Unique so two descriptors can never claim the same object — which would make deletion of one silently break the other. |
| `SizeBytes` | `int` | required, `> 0` | Serves the descriptor's "describe a fetch without touching the store" duty (FR-006) and lets `Content-Length` and quota checks work without a store round-trip. |

`ContentType` is unchanged (`HasMaxLength(64)`, required). After 034 every stored object is WebP, but
the column stays because the descriptor must remain self-describing (FR-006) and future kinds may differ.

## What deliberately does NOT change

- **`ProfileAvatar`'s ban filter.** `AppDbContext` keeps
  `entity.HasQueryFilter(a => a.Profile.User.Status != AccountStatus.Banned)` exactly as written. This is
  what makes FR-010's ban guarantee structural rather than remembered. Preserving it is the reason the
  three tables were not merged.
- **The unique index on the owner FK** (`ProfileId`, etc.) — still one media object per owner.
- **Cascade delete from the owner** — satisfies the descriptor half of FR-009 unchanged.

  ⚠️ **The object half does not come for free.** All three entities are configured
  `OnDelete(DeleteBehavior.Cascade)`, and `User → PlayerProfile` cascades too, so those deletes execute
  **inside PostgreSQL**. No application code runs, and therefore no blob is deleted — the object is
  silently orphaned. Today this is **latent rather than active**: nothing hard-deletes a user, a
  profile, or a badge/achievement definition (bans are soft-delete per 013; catalogue definitions
  retire and reinstate per 014), and the only real deletions are the explicit `Remove(icon)` calls in
  `BadgeService` and `AchievementService` plus avatar replacement — all of which *are* application code.

  The rule that follows: **delete the object explicitly wherever application code deletes media**, and
  treat the FR-030 reconciliation sweep as the guaranteed backstop for anything a future cascade path
  removes underneath us. A hard-delete path added later (GDPR erasure is the obvious candidate) would
  otherwise orphan blobs silently, with nothing failing.

## Object key layout

```
{kind}/{32-hex}.webp        e.g.  avatars/9f2c4d1ab7e04c6f8a3d5e21bc09f4a7.webp
                                  badge-icons/1c7e…​.webp
                                  achievement-icons/44b0…​.webp
```

- Generated by `MediaObjectKey`, once per upload, **before** the first store attempt — which is what
  makes a retried write idempotent (it overwrites the same key rather than creating a second object).
- Random **UUIDv4**, not UUIDv7 — see research §5 for why this is a reasoned divergence from the
  Principle III key rule rather than an oversight.
- The `{kind}` prefix is for operator legibility and lifecycle rules only. It is **not** a security
  boundary: the container is private as a whole (FR-012), and prefixes must never be used to grant
  differential public access.

## Migration (single, no backfill)

Owner decision: existing media is discarded (spec Clarifications). The migration therefore does, in order:

1. **`DELETE FROM "ProfileAvatars"` / `"BadgeIcons"` / `"AchievementIcons"`** — required by FR-019.
   A surviving row would point at an object that was never written, which is the exact
   "record without object" edge case the spec calls out. Deleting first also removes any need for a
   default value when adding non-nullable columns.
2. **Drop column `Bytes`** from all three tables.
3. **Add `ObjectKey` (text, not null)** and **`SizeBytes` (integer, not null)**; create the unique
   index on `ObjectKey` per table.

Re-applying is a no-op (FR-020/SC-007): EF records the migration, and the resulting schema is identical.

**Post-cutover state**: every member sees the standard no-picture placeholder and can upload again; an
administrator re-uploads catalogue icons through the existing admin surface (FR-021). No new tooling.

## Configuration

`MediaStorageOptions` (bound from `MediaStorage:*`, safe defaults, identical shape in every environment):

| Setting | Default | Notes |
|---|---|---|
| `ConnectionString` | — | Azurite locally (published dev credential, annotated); real account key from GitHub Environments when deployed. |
| `ContainerName` | `media` | Same in every environment; isolation comes from separate **accounts** per environment (FR-025), not from container names. |
| `CacheRevalidate` | `true` | Emits `Cache-Control: private, no-cache` — never `public` (shared caches), and never a long freshness window, which would let a banned or newly-private member keep rendering in a viewer's browser and break FR-016 (research §9). |
| `OrphanGraceMinutes` | `60` | Sweep ignores objects newer than this so in-flight uploads are not reclaimed. |

Resilience lives in its own section, `Resilience:Outbound:MediaStore` (research §4), not here — one
integration, one resilience section, per Principle VII.

## Validation rules

- `ObjectKey` non-empty, ≤ 200 chars, unique per table.
- `SizeBytes` > 0 and ≤ the processed-output ceiling already enforced by `IImageProcessor` (034). This
  feature does **not** re-validate image content (FR-005) — it stores what the processor returned.
- A descriptor row is written **only after** its object is confirmed stored, so the invariant
  "every descriptor points at a real object" holds at commit time.
